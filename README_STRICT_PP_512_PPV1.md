# STRICT PP GR (512×512, PPV1) — Scalar + Vector Overview

This note summarizes the **STRICT PP** General Relativity status at scale **512×512 (PPV1)** for:

- **Scalar observables** (τ-geometry, Shapiro, perihelion, deflection front), and  
- **Vector-like observables** (azimuthal circulation, frame-dragging proxy, feeder-shear, ring gradient correlation).

Shared constraints:

- Distance and time are purely **Markov / PP**:
  - Doyle / commute-time distances and Markov hop counts.
- Geometry is built from **traces and partial order** only (PPV1 edge policy + trace weights).
- No PDE, no Laplacian/Poisson, no GR ansatz, no regression are allowed in the STRICT-PP 512 pipeline.
- Coordinates and “angles” are used only as **labels** (for binning/ordering), not as rulers.

---

This repo contains two STRICT-PP edge families at 512×512:

- **PPV1 (baseline / archival):**
  - `edges_ca_v3_*_512x512_PPV1.txt`

  - `edges_ca_v3_*_512x512_PPV1_E2.txt`

Policy:

- **Scalar/vector EFE status summaries in this README refer to PPV1** unless explicitly labeled `PPV1_E2`.
- **Deflection-front and other transport/off-diagonal/front tests should use PPV1_E2** at 512×512 because it restores broad directed reachability while remaining STRICT PP.

This is not “tuning per run”: PPV1_E2 is a fixed, versioned, trace→edges policy reused across cases with distinct filenames.

### 1.2 Deflection — STRICT PP Markov front (512×512 PPV1)

Deflection is probed via `PP_deflection_markov_front_PP_v6.py`:

```bash
python src/gr_strict_pp_scalar/PP_deflection_markov_front_PP_v6.py \
  --edges_flat edges_ca_v3_flat_512x512_PPV1.txt \
  --edges_curved edges_ca_v3_strong_pf010_512x512_PPV1.txt \
  --H 512 --W 512 \
  --mass_mask PP_mass_mask_512x512_strong_pf010_PPV1.npy \
  --orbit_mask PP_orbit_ring_mask_512x512_strong_pf010_PPV1.npy \
  --steps 512 \
  --burn_in 64 \
  --window 128 \
  --min_front_mass 1e-4 \
  --min_ring_nodes 100 \
  --delta_threshold 0.05 \
  --source_band_width 4 \
  --output src/gr_strict_pp_scalar/PP_deflection_markov_front_512_strong_pf010_v6_PPV1.json
```

Observable (strict PP):

* Sources are defined **only** by Markov hop distance to mass on the flat graph (max-distance band).
* Candidate “rings” are defined **only** by Markov hop distance to mass plus a fixed orbit mask (outer band).
* Deflection would be a difference in time-averaged front mass on that ring:
  (\Delta D = D_{\text{curved}} - D_{\text{flat}}).

Status (strong_pf010, 512×512 PPV1):

* `APPLICABLE = False`
* Reason:
  *“No Markov hop-distance band (d>0) with sufficient nodes and nonzero flat/curved front mass.”*

Interpretation:

* With this CA/trace-derived geometry, Markov fronts launched from the max-distance band do not deliver a usable grazing flux to any Markov-defined ring around the mass in both flat and curved cases.
* Deflection for this 512×512 PPV1 configuration is therefore recorded as **NA / not established** under STRICT PP, rather than forced by tuning.

### 2.3 Aggregation keys (v1 vs v2)

Each vector pack exposes two overall keys:

* `overall_PASS_vector_strict_PP_v1`
  Legacy strict gate (all applicable proxies must pass):
  uses `PASS_azimuthal_or_NA`, `PASS_frame_dragging_or_NA`, `PASS_feeder_shear_or_NA`.

* `overall_PASS_vector_strict_PP_v2`
  **512-aware aggregation**:

  * At `H ≥ 512`, feeder-shear is kept as **informative but non-gating** due to saturation under PPV1 edges.
  * Gate is: `PASS_azimuthal_or_NA` and `PASS_frame_dragging_or_NA`.
  * Below 512, v2 falls back to v1.

The suite v2 prefers v2 if present; otherwise falls back to v1.

For 512×512 PPV1:

* `overall_PASS_vector_strict_PP_v1 = False` (both cases)
* `overall_PASS_vector_strict_PP_v2 = True` (both cases)
* `ALL_PASS_vector_strict_PP_v2 = True` (suite)

What we **do not** yet claim:

In other words:

* At STRICT PP 512×512, we have:

  * A **strong scalar EFE-00 result**,
  * A **positive, but conservative, vector sector** from ring-local Markov observables,
  * And a clearly documented boundary: full 3+1 tensor (G_{\mu\nu}) remains open work, not a claim.

This overview is intended as a **stable snapshot** of the STRICT PP 512×512 PPV1 state. Future work should extend or refine it, not contradict it.
