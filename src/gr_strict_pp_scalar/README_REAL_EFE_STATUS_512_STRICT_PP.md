# REAL EFE 512 STRICT PP — Status Chain (v2)

This document defines the **status-only** reproducibility step for the 512×512 STRICT PP “REAL EFE” result.

It does **not** regenerate any physics artifacts. It only **audits wiring** and produces a final PASS/FAIL JSON from already-produced component status JSONs.

---

## What this runner does

The runner `run_REAL_EFE_status_512_STRICT_PP_v2.sh` executes three steps:

1) **Tensor 3+1 status binder**
- Script: `PP_EFE_tensor_3p1_status_512_STRICT_PP_v1.py`
- Purpose: resolve a single boolean for “3+1 tensor status PASS” by checking:
  - a key in the master status JSON (preferred), else
  - fallback to tensor_2p1 status JSON,
  - optionally gates on invariance if provided (we allow NA here).

2) **REAL EFE status binder**
- Script: `PP_EFE_real_EFE_status_512_STRICT_PP_v2.py`
- Purpose: compute `ALL_PASS_real_EFE_strict_PP_512_v2` as the AND of:
  - scalar A2b status,
  - offdiag 2p1 status,
  - bianchi status,
  - tensor closure status,
  - tensor 3p1 status (from step 1).
- Notes:
  - This script records the **paths** used under `.inputs`.
  - Invariance is not required by default (`require_invariance=false`).

3) **Final wrapper**
- Script: `PP_EFE_real_EFE_final_status_512_STRICT_PP_v2.py`
- Purpose: write a compact final JSON containing `FINAL_PASS_real_EFE_512_STRICT_PP_v2` derived from the REAL EFE binder JSON.

## What is verified (and what is not)

### Verified by this runner
- The **status-chain wiring** is consistent and reproducible.
- The final PASS reflects:
  - `scalar_A2b PASS`
  - `offdiag PASS`
  - `bianchi PASS`
  - `closure PASS`
  - `tensor3p1 PASS`
- The produced binder JSON records the exact input paths under `.inputs`.

### Not verified by this runner
This runner does **not**:
- regenerate edges, lengths, flows, Tmunu, geometry, or any intermediate NPZs,
- rerun any expensive GPU compute kernels,
- re-audit mathematics of kernels (use the math audit harnesses for that),
- validate that the theoretical identification “this operator equals that GR object” is correct.

If you want kernel-level validation, run the relevant audit harness suite(s) separately and check them into `runs/audits/` (or a repo-tracked location you standardize).

## Notes on CLI flags

* Some status scripts record `--device` only (or do not accept it at all). The runner uses the correct flags for each script.
* `PP_EFE_real_EFE_status_512_STRICT_PP_v2.py` does **not** accept `--device` or `--allow_na_invariance`.
* `PP_EFE_real_EFE_final_status_512_STRICT_PP_v2.py` only accepts:

  * `--real_efe_json`
  * `--output`
  * optional `--hash`

This is intentional: these scripts are binders/wrappers, not compute kernels.
